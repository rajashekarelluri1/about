Every DAX category you'll actually reach for, searchable by name or keyword. ★ marks the measures you'll write every single week.

01

Getting Started — The Power BI Interface

Three views, one file. Understanding what each one is for prevents most beginner confusion.

1.1

Report View

Where you build visuals on a canvas — drag fields, format charts, arrange pages. This is what end users see when a report is shared.

1.2

Data View

A spreadsheet-like look at every loaded table, row by row. Use it to sanity-check that a transformation or DAX column actually did what you expected.

1.3

Model View

The relationship diagram between all your tables — the single most important view for keeping a report accurate as it grows.

1.4

Fields pane

Every table and column across your model, searchable. Right-click to rename, hide, or create a new measure without leaving the canvas.

1.5

Filters pane

Three scopes — visual, page, and report level — each stacking on top of the others. A visual showing the "wrong" number is almost always an upstream filter.

1.6

Formatting pane

Per-visual styling — titles, colors, data labels, conditional formatting. Save a theme once your palette is set, so every new report starts consistent.

02

Get Data & Power Query

The same Power Query engine as Excel, with more connectors — this is where messy source data becomes a clean, load-ready table.

2.1 Common data sources+
Excel / CSV SQL Server SharePoint Web / API Dataverse Google BigQuery Azure Synapse
2.2 Import vs DirectQuery+

Import copies data into the model — fast, fully-featured DAX, needs a refresh schedule. DirectQuery queries the source live on every interaction — always current, but slower and with some DAX limitations. Most reports should default to Import unless the data is too large or must be real-time.

2.3 Query folding+

Power Query pushes transformation steps back to the source database when possible, instead of pulling raw data and filtering locally. Keep folding-breaking steps (like custom columns with M functions) as late in the query as possible to preserve performance.

2.4 Parameters+

Define a reusable value — a file path, a date, an environment name — once, and reference it across every query. Switching a report from a test to a production data source becomes a one-line change instead of editing every query.

03

Data Modeling

The single biggest skill gap between a beginner and an intermediate Power BI user. Get the model right and DAX becomes simple; get it wrong and every measure fights you.

3.1 Star schema+

One central fact table (transactions, sales, events — the "what happened") connected to several dimension tables (Date, Product, Customer, Region — the "how do I slice it"). This shape is what Power BI's engine is optimized for.

3.2 Relationships & cardinality+

Most relationships should be one-to-many, filtering in a single direction from dimension to fact. Bidirectional filtering looks convenient but can silently cause ambiguous or duplicated results as the model grows — use it deliberately, not by default.

3.3 The Date table+

Every model with time-based analysis needs one dedicated Date table, marked as the official date table (Model view → right-click table → Mark as date table). Nearly every time-intelligence DAX function depends on this being set up correctly.

-- A basic calculated Date table
DateTable = CALENDAR(DATE(2023,1,1), DATE(2026,12,31))
3.4 Calculated columns vs measures+

A calculated column is computed row-by-row and stored in the model (uses memory, refresh time). A measure is computed on the fly based on whatever's currently filtered (no storage cost, always context-aware). Default to measures; reach for columns only when you need to filter, sort, or slice by the result.

04

DAX Fundamentals

The concept that unlocks everything else in DAX: every formula evaluates inside a context, and that context changes what the same formula returns.

4.1 Row context vs filter context+

Row context exists inside calculated columns and iterator functions (SUMX, FILTER) — DAX evaluates the formula once per row. Filter context is whatever's currently sliced, filtered, or grouped by a visual — it's why the same measure returns a different number in every cell of a matrix.

4.2 CALCULATE — the most important function in DAX+

CALCULATE evaluates an expression inside a modified filter context. Nearly every non-trivial measure is CALCULATE wrapping something simpler.

-- Sales, ignoring whatever region is currently filtered
All Region Sales = CALCULATE([Total Sales], ALL(Region))

-- Sales for just the "Online" channel, regardless of slicer selection
Online Sales = CALCULATE([Total Sales], Channel[Type] = "Online")
4.3 Variables (VAR / RETURN)+

Name an intermediate calculation once, reuse it, and make the formula readable — the DAX equivalent of Excel's LET.

VAR CurrentSales = SUM(Sales[Amount])
VAR PriorSales = CALCULATE(SUM(Sales[Amount]), SAMEPERIODLASTYEAR('Date'[Date]))
RETURN DIVIDE(CurrentSales - PriorSales, PriorSales)
4.4 DIVIDE over the / operator+

DIVIDE(numerator, denominator, [alternate]) handles divide-by-zero gracefully and returns a clean alternate value (often blank or 0) instead of an error breaking the visual.

05

Time Intelligence

YTD, growth-over-prior-period, rolling averages — the calculations every stakeholder asks for, built on a correctly marked Date table.

5.1 YTD / QTD / MTD+
Sales YTD = TOTALYTD([Total Sales], 'Date'[Date])
Sales QTD = TOTALQTD([Total Sales], 'Date'[Date])
Sales MTD = TOTALMTD([Total Sales], 'Date'[Date])
5.2 Year-over-year comparison+
VAR PriorYear = CALCULATE([Total Sales], SAMEPERIODLASTYEAR('Date'[Date]))
RETURN DIVIDE([Total Sales] - PriorYear, PriorYear)
5.3 Rolling windows+

DATESINPERIOD('Date'[Date], LASTDATE('Date'[Date]), -12, MONTH) inside a CALCULATE builds a rolling 12-month view — useful for smoothing seasonal spikes out of a trend line.

06

Visualizations

Choosing the right chart matters more than making it pretty — the wrong shape makes a correct number look wrong.

6.1

Line & area charts

Trend over time. Use area sparingly — stacked areas are hard to compare accurately above the bottom layer.

6.2

Bar & column charts

Comparison across categories. Horizontal bars read better with long category names.

6.3

Matrix & table

When exact numbers matter more than the shape of the data — finance and audit-style reports lean on these heavily.

6.4

Cards & KPIs

One headline number, always visible, usually top-left — the answer to the single most important question on the page.

6.5

Slicers

Turn one report into many views. Sync slicers across pages via View → Sync slicers so a filter choice persists as users navigate.

6.6

Custom visuals (AppSource)

Use sparingly — native visuals load faster and behave more predictably. Reach for custom visuals only when a native chart genuinely can't do the job.

07

Reports, Bookmarks & Drill-through

Interactivity is what separates a Power BI report from a static export — these features turn one page into a guided experience.

7.1 Bookmarks+

Capture the exact state of a page — filters, slicer selections, visibility — and return to it with a button click. Commonly used to build toggle-able views ("Summary" vs "Detail") on the same page.

7.2 Drill-through+

Right-click a data point to jump to a detail page pre-filtered to that context — e.g. click a region on a map to land on a page showing only that region's accounts.

7.3 Tooltip pages+

A small report page shown on hover instead of the default tooltip — useful for showing a mini trend chart without cluttering the main visual.

7.4 Mobile layout+

Design a separate phone-optimized layout in View → Mobile Layout — stakeholders checking a dashboard from their phone are a real and common audience.

08

Row-Level Security (RLS)

One report, many audiences — each user sees only the rows relevant to them, without maintaining separate report copies.

8.1 Static roles+

Define a role in Modeling → Manage roles with a DAX filter, then map users or groups to it in the Power BI Service.

-- Role filter on the Region table
[Region] = USERPRINCIPALNAME()
8.2 Dynamic RLS+

Map users to allowed values in a table inside the model itself, rather than hardcoding per-role filters — scales to hundreds of users without creating a new role for each one.

8.3 Testing RLS+

Use View as in Desktop before publishing — RLS bugs are much cheaper to catch locally than after a user reports seeing the wrong data.

09

Publishing & The Power BI Service

A report only creates value once someone else can see it, on schedule, with current data.

9.1

Workspaces

The container for related reports, datasets, and dashboards — organize by team or project, not by individual report.

9.2

Apps

A packaged, read-only view of a workspace's content, distributed to a wider audience without giving them edit access.

9.3

Scheduled refresh

Set how often an Import-mode dataset pulls fresh data from its source — requires a gateway if the source is on-premises.

9.4

On-premises data gateway

A bridge that lets the cloud-hosted Power BI Service securely reach data sources that live inside a private network.

9.5

Dashboards vs Reports

Reports are multi-page and interactive; dashboards are a single pinned-tile summary, often built by combining visuals from several reports.

9.6

Sharing & permissions

Share at the workspace, app, or individual report level — match the scope to how much of the underlying data the recipient should actually see.

10

Performance Optimization

A report that takes ten seconds to load per click will quietly stop being used, no matter how correct the numbers are.

10.1 Model size discipline+

Remove unused columns before loading — every extra column increases file size and refresh time. Prefer star schema over one giant flat table; a well-modeled star schema compresses and queries far better.

10.2 Performance Analyzer+

View → Performance Analyzer shows exactly how long each visual took to query, render, and load on the current page — the first stop when a report feels slow.

10.3 DAX Studio & Tabular Editor+

Free external tools for profiling slow measures (DAX Studio) and bulk-editing model metadata faster than the native UI (Tabular Editor) — standard kit once you're managing larger models.

10.4 Avoid over-using bidirectional filters and iterators+

Bidirectional relationships and row-by-row iterator functions (SUMX over huge tables) are the two most common causes of a model that feels fine at 10,000 rows and grinds at 10 million.

12

Suggested Learning Path

A realistic order to build these skills — each stage assumes roughly two to three weeks of applied practice on real or realistic data.

Weeks 1–2 — Interface & first report

Explore Report/Data/Model views, connect to an Excel or CSV source, build a simple page with 3–4 visuals and slicers.

Weeks 3–4 — Power Query & data modeling

Clean a messy multi-table dataset, build a star schema, set relationships, and mark a proper Date table.

Weeks 5–7 — DAX fundamentals

Write measures using CALCULATE, FILTER, and variables. Rebuild the same KPI as a calculated column and a measure to feel the difference.

Weeks 8–9 — Time intelligence

Build YTD, YoY growth, and a rolling 12-month trend on top of your Date table.

Weeks 10–11 — Interactivity & security

Add bookmarks, drill-through pages, and set up Row-Level Security with at least one dynamic role.

Weeks 12+ — Publish, optimize, and iterate

Publish to a workspace, set a refresh schedule, then use Performance Analyzer to find and fix the slowest visual on your busiest page.
